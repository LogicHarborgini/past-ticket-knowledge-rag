## Scores

| Metric | Score | Reading |
|---|---|---|
| Faithfulness | — | Are the claims in the answer supported by the retrieved tickets? |
| Answer relevancy | — | Does the answer address the question that was asked? |
| Context precision | — | Were the retrieved tickets relevant to the question? |
| Context recall | — | Did retrieval return everything the reference answer needed? |

Configuration for the run: _generation model_, _embedding model_, _judge model_,
_k_, _date_ — all recorded automatically in `evals/ragas_baseline.json`.

## How to produce these numbers

RAGAS and this application cannot share a virtualenv: RAGAS imports
`langchain_community.chat_models.vertexai`, which the LangChain 1.x line removed.
So evaluation is two steps with a JSON file between them.

```bash
# 1. Application environment — run the pipeline over the eval questions
LLM_PROVIDER=bedrock python -m evals.ragas_collect
#    → evals/ragas_samples.json

# 2. Evaluation environment — score those samples
python -m venv .venv-evals
.venv-evals/Scripts/pip install -r requirements-evals.txt
.venv-evals/Scripts/python -m evals.ragas_eval
#    → evals/ragas_baseline.json  (+ a printed reading of what to fix first)
```

`ragas_collect` refuses nothing but warns on `LLM_PROVIDER=fake`; `ragas_eval`
refuses fake samples outright, because scoring a canned string spends judge
tokens measuring nothing.

The samples file is a durable artefact. Rescoring it with different metrics, or
diffing two prompt versions, costs judge tokens only — the pipeline does not have
to run again.

## The evaluation set

Six questions in `evals/ragas_collect.py`, each with a hand-written ground-truth
answer taken from the corpus rather than generated by a model. A reference
written by an LLM measures agreement with that LLM, which is not correctness, and
it silently caps every score at the reference model's quality.

Five questions have an answer in the corpus. The sixth — an office seating plan —
does not, and the correct behaviour is refusal. A pipeline that scores well on
the first five and invents an answer for the sixth is not a good pipeline; it is
one that has never been asked a question it cannot answer.

## Reading the scores

The single most useful thing here is the pair, not any individual number:

| Faithfulness | Context precision | Diagnosis |
|---|---|---|
| Low | Low | Retrieval is feeding the model poor context and the model is filling the gap itself. Fix retrieval first — no prompt can ground an answer in documents that were never retrieved. |
| Low | High | The right tickets came back and the model added claims they do not support. Prompt problem: tighten the grounding instruction. |
| High | Low | The model is ignoring the noise it was handed. Works until it does not. Lower `RETRIEVAL_TOP_K` or set `RETRIEVAL_SCORE_THRESHOLD`. |
| High | High | Working as intended. Look at answer relevancy next. |

`evals/ragas_eval.py` prints this reading automatically and names the weakest
metric, so the output says what to fix rather than only what the score was.

## Regression tracking

Re-run after any change to the system prompt, the model, `k`, the corpus, or the
chunking. A drop greater than 0.05 on any metric is reported as a regression and
the script exits non-zero, so it can gate a CI job later.

Two guards against false signals:

- **Judge changes invalidate comparison.** Two judges disagree with each other
  more than a prompt change moves either of them, so a run judged by Claude is
  not compared against a baseline judged by a local model.
- **0.05, not 0.01.** LLM-as-judge scoring is not deterministic even at
  temperature 0. A tighter threshold would fire on the judge's own variance.

## Known limitations

- **The judge is an LLM.** Its scores carry its own biases, and a small local
  model follows the RAGAS rubric loosely enough to produce NaNs where it breaks
  the JSON contract. `ragas_eval` tolerates those rather than failing the run, but
  a metric scored on three of six samples is worth less than one scored on six.
- **Six questions is a development baseline, not a quality gate.** It is enough
  to catch a regression from a prompt change; it is not enough to certify a
  system. Production would grow this set from real queries that went wrong.
- **Absolute values are not portable.** 0.8 faithfulness is fine for suggesting
  what an engineer should try and unacceptable for anything acted on without
  review. The number only means something next to what depends on it.
- **RAGAS scores each question in isolation.** It says nothing about consistency
  across a session or how the pipeline handles a follow-up question.
